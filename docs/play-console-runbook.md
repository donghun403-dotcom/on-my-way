개발자 계정 승인 직후부터 내부 테스트 출시·결제 연결까지의 순서다. **콘솔 화면 순서

표기: **[결정]** 이 문서에서 확정한 답 · **[사용자]** 내가 대신할 수 없는 입력 ·
**[확인 필요]** 콘솔 화면에서 실제 문항을 보고 판단

## 0. 시작 전 — 계정 유형부터 본다

**설정 → 개발자 계정 → 계정 정보**에서 계정 유형을 확인한다. 이 값 하나가 출시
경로를 가른다.

| 계정 유형 | 프로덕션까지의 경로 |
| --- | --- |
| **조직(Organization)** | 내부 테스트 → 바로 프로덕션 신청 가능 |
| **개인(Individual)** | 2023-11 이후 만든 계정은 **비공개 테스트에 테스터 12명이 14일 연속** 참여해야 프로덕션 신청이 열린다 |

**확정: 개인 계정이다(2026-08-04 확인).** 따라서 **비공개 테스트 14일이 이 프로젝트의
최장 경로**이고, 아래 순서는 전부 그 시계를 가장 빨리 돌리기 위해 배열돼 있다.

### 개인 계정의 임계 경로

```
앱 생성 → 선언 전부 → 등록정보 → 비공개 테스트 업로드(심사) → 테스터 12명 옵트인
                                                              └─ 여기서 14일 시계 시작
```

**시계는 "12명이 실제로 참여(옵트인)한 시점"부터 센다.** 업로드한 날이 아니다. 그래서
지금 할 일의 우선순위는 ① 심사를 통과시키는 것 ② 12명을 모으는 것 둘이고, 나머지
(결제 상품·RTDN 배선)는 그 14일 **안에** 병렬로 하면 일정에 영향을 주지 않는다.

**내부 테스트는 별개로 같이 연다.** 내부 테스트는 심사가 없어 즉시 설치 링크가 나오므로
본인 기기 검증용으로 쓰고, 14일 요건은 **비공개 테스트만 인정된다.**

**[확인 필요]** 요건의 정확한 숫자(12명·14일)는 콘솔의 **「프로덕션 액세스 신청」**
화면에 현재 기준으로 표시된다. 시작 전에 그 화면을 한 번 열어 숫자를 확인하는 것이
안전하다 — 구글이 기준을 바꾸면 이 문서보다 그 화면이 맞다.

### 테스터 12명 — 지금부터 모아야 한다

- 이메일 목록에 등록된 **구글 계정**이어야 하고, 각자 테스트 링크로 **직접 옵트인**해야
  한다. 설치까지 하면 확실하다.
- 14일 동안 **계속 참여 상태를 유지**해야 한다. 중간에 옵트아웃하면 그 인원이 빠진다.
- 12명은 하한이다. **14~15명을 모으는 편이 안전하다** — 한두 명이 중간에 빠져도 요건이
  깨지지 않는다.
- 가족·지인이 가장 확실한 경로다. `@ollie_is_on_myway` 계정은 팔로워 규모상 12명 모집을
  기대할 채널이 아직 아니다(`brand/marketing/account.md`).

## 4. 테스트 트랙 출시 — 두 개를 함께 연다

개인 계정이므로 **비공개 테스트가 일정의 본선**이고 내부 테스트는 본인 검증용이다(§0).

| 항목 | 값 |
| --- | --- |

| Play 앱 서명 | 첫 업로드 시 자동 등록 — 우리 PKCS12는 **업로드 키**가 된다 |

번들 + Play 재서명**이라 서명 경로가 바뀌었다. 한 번은 돌려 봐야 한다.

### 4.2 비공개 테스트 (14일 요건 — 심사 있음)

**테스트 및 출시 → 테스트 → 비공개 테스트 → 새 버전 만들기**

같은 `vc2` AAB를 올린다. 내부 테스트와 달리 **심사를 거치므로 §2의 선언과 §3의 등록정보가
모두 끝나 있어야** 제출할 수 있다.

- 테스터: 이메일 목록을 만들어 **14~15명**을 넣는다(하한 12명, 여유 포함 — §0)
- 출시 후 나오는 **참여 링크(opt-in URL)** 를 각자에게 보내고, **각자 그 링크로 참여를

- 진행 상황은 **프로덕션 액세스 신청** 화면에서 "며칠째 / 몇 명"으로 확인한다.

| 무료 체험 | **제공하지 않음** **[결정]** |

**무료 체험을 스토어에 만들지 않는 이유**: 우리 체험은 서버가 관리한다(가입 시 시작,
계정당 1회, 남용 마커까지). 스토어 체험을 겹치면 체험 상태가 두 곳에 생기고 어느 쪽이
진실인지 물어야 한다 — `docs/entitlement-schema-draft.md` §0이 경고하는 형태다.

### 5.2 API 액세스 (구매 검증용)

**설정 → API 액세스**

1. Google Cloud 프로젝트를 새로 만들어 연결
2. 서비스 계정 만들기 → **JSON 키 다운로드**
3. Play Console에서 그 서비스 계정에 권한 부여: **재무 데이터 보기** + **주문 및 구독 관리**

**[확인 필요]** 권한 전파에 시간이 걸릴 수 있다(구글 문서상 최대 24시간). 검증
엔드포인트가 403을 주면 이것부터 의심한다.

### 5.3 실시간 개발자 알림(RTDN)

1. Google Cloud → **Pub/Sub → 주제 만들기**
2. 그 주제에 `google-play-developer-notifications@system.gserviceaccount.com`을
   **게시자(Pub/Sub Publisher)** 로 추가
3. Play Console → **수익 창출 설정 → 실시간 개발자 알림** → 주제 이름 입력 →
   **테스트 알림 보내기**
4. Pub/Sub에서 **푸시 구독** 만들기 → 엔드포인트:
   `https://onmyway.olivenrich.com/api/billing/google/rtdn?token=<GOOGLE_RTDN_PUSH_TOKEN>`

토큰은 내가 난수로 만들어 시크릿으로 등록한다(§6). 3번의 테스트 알림이 우리 서버에
`outcome: "test"`로 기록되면 배선이 끝난 것이다.

## 6. 우리 쪽 구성 (콘솔이 끝난 뒤 — 내가 한다)

콘솔에서 나온 값들을 서버에 꽂는 단계다. **서비스 계정 JSON은 내가 열지 않는다** —
`wrangler secret put`이 표준입력으로 받으므로 값이 내 눈에 들어오지 않는다.

1. **D1 데이터베이스** — 운영에 `BILLING_DB` 바인딩이 아직 없다. 만들고 바인딩한 뒤
   `migrations/0001`·`0002`를 적용한다.
2. **시크릿 3개**

```bash
npx wrangler secret put GOOGLE_PLAY_SERVICE_ACCOUNT_JSON
```

```bash
npx wrangler secret put GOOGLE_RTDN_PUSH_TOKEN
```

3. **vars**: `GOOGLE_PLAY_PACKAGE_NAME = "com.olivenrich.onmyway"` (비밀이 아니다)
4. 구성이 들어가면 `/api/billing/google/verify`가 503에서 깨어난다. 그 전까지는 두
   엔드포인트 모두 닫혀 있다.
