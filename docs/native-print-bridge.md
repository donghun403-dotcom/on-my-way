# 네이티브 인쇄 브릿지 조사 (2026-07-30)

**조사만이다. 코드를 고치지 않았다.**

## 0. 무엇이 문제인가

**[코드]** `script.js:9790-9814` `printDiaryBook()`:

```js
window.addEventListener("afterprint", restore);
window.setTimeout(restore, 60_000);
try {
  window.print();
} catch (error) {
  console.warn("Unable to open print dialog", error);
  restore();
}
```

Android WebView와 iOS WKWebView는 **`window.print()`를 구현하지 않는다.**
**예외도 던지지 않는다.** 그래서:

- `catch`가 발동하지 않아 `restore()`가 즉시 호출되지 않는다
- `afterprint`도 오지 않는다 (인쇄가 시작된 적이 없으므로)
- **60초 타임아웃만 남는다** — `body.is-printing-book`이 붙은 채로 1분

**정정 — 이 문서의 첫 판은 "60초 동안 조판된 인쇄 화면에 갇힌다"고 적었다. 틀렸다.**
**[코드]** `.diary-book-print { display: none }`은 화면 스타일시트에 있고
`is-printing-book` 규칙은 **전부 `@media print` 안**이다(`styles.css:18827-18829`).
그래서 화면은 바뀌지 않는다.

유저가 보는 것: **Pro 기능을 눌렀는데 아무 일도 일어나지 않는다.** 오류 메시지도 없다.
그리고 60초 동안 **`document.title`이 "올리 다이어리 북 …"으로 남는다** — 그 사이에
유저가 다른 것을 인쇄하거나 페이지를 저장하면 파일명이 그 값으로 나간다.

증상은 덜 극적이지만 판단은 바뀌지 않는다. 유료 기능이 침묵으로 실패하고, 유저가 다시
누르는 것 말고 할 수 있는 일이 없다.

**[미검증]** 실기기에서 재현하지 못했다. `docs/capacitor-shell-checklist.md`의 A-9/B-9가
이걸 잰다. **Pro 계정이 필요하다** — **[코드]** `script.js:9791`의 `canCreateDiaryBook()`이
먼저 막는다.

## 0.1 같은 자리에서 발견한 것 — `.md` 내보내기도 위험하다

인쇄보다 먼저 봐야 할 수 있다.

**[코드]** `script.js:1143-1153` `exportRecordsFile()`:

```js
const url = URL.createObjectURL(new Blob([markdown], …));
const link = document.createElement("a");
link.href = url;
link.download = `on-my-way-기록-….md`;
link.click();
```

Android WebView는 `<a download>`와 `blob:` URL을 **기본적으로 처리하지 않는다.**
네이티브 쪽에 `DownloadListener`(또는 그에 준하는 처리)가 붙어 있어야 파일이 저장된다.
Capacitor 기본 `BridgeActivity`가 이걸 붙여 주는지는 **[미검증]**이다.

**왜 인쇄보다 급한가**: `.md` 내보내기는 **만료 계정에도 열려 있어야 하는 항목**이다.
**[코드]** `plan-policy.mjs:38,55`가 `expired`·`trial_pending`에도 `basicRecords: true`를
주고, **[코드]** `script.js:4954`의 주석이 그 이유를 "무료 `.md` 내보내기는 만료
계정에서도 반드시 되어야 하는 법적 요건"이라고 적고 있다. 개인정보 자기결정권 —
내 기록을 가져갈 수 있어야 한다.

**인쇄가 깨지면 Pro 기능 하나가 죽는다. `.md`가 깨지면 법적 요건이 죽는다.**
체크리스트에 항목을 추가해야 한다 — 이번 회차에는 하지 않았다(문서만 지시).

## 3. 후보 비교

### 후보 A — Capacitor 인쇄 플러그인 (`@capacitor-community/printer` 등)

Android `PrintManager` + `WebView.createPrintDocumentAdapter()`, iOS
`UIPrintInteractionController`를 감싼다.

| | |
| --- | --- |
| **비용** | **낮음.** 플러그인 1개 + `printDiaryBook()`에 분기 몇 줄 |
| **인쇄 CSS** | **그대로 재사용된다.** Android의 `createPrintDocumentAdapter()`는 WebView 콘텐츠를 인쇄 스택으로 넘기므로 `@media print` 101줄이 적용된다 — **이게 이 후보의 핵심 이점이다** |
| **Pro 게이트** | 지금 자리 그대로. 분기는 `canCreateDiaryBook()` **뒤**에 둔다 |
| **웹 경로** | 무영향. 네이티브에서만 분기 |
| **결과물** | 시스템 인쇄 대화상자 → 프린터 또는 "PDF로 저장" |
| **iOS** | 같은 플러그인이 처리 |

**위험**

- **[확인 필요]** `@capacitor-community/printer`의 Capacitor 8 지원 여부와 유지 상태.
  커뮤니티 플러그인이라 메이저 업그레이드에서 멈추는 일이 흔하다.
- **[미검증]** Android가 인쇄하는 것이 **화면 상태 그대로**인지, `@media print`를 적용한
  상태인지. `body.is-printing-book` 클래스가 붙은 채로 넘겨야 할 수도 있다.
- **[코드]** `mobile/README.md`에 적은 대로 지금은 `mobile/android/`를 커밋하지 않는다.
  플러그인은 Capacitor가 자동 링크하므로 **이 결정은 그대로 유지된다** — 네이티브 코드를
  우리가 쓰지 않기 때문이다.

**막히면**: 플러그인이 죽어 있으면 같은 API를 부르는 커스텀 플러그인을 직접 쓴다.
Android는 20줄 남짓, iOS도 비슷하다. 그 순간 `mobile/android/`를 커밋해야 한다.

### 후보 B — 클라이언트 PDF 생성 (jsPDF / html2pdf 등) + 파일 저장·공유

| | |
| --- | --- |
| **비용** | **높음** |
| **인쇄 CSS** | **버려진다.** jsPDF는 `@media print`를 해석하지 않는다. **101줄 + `.book-*` 60줄을 PDF 좌표로 다시 짜야 한다** |
| **Pro 게이트** | 지금 자리 그대로 |
| **웹 경로** | 웹도 이쪽으로 통일할 수 있지만, 그러면 현재 정상 동작하는 경로를 버리는 것이다 |
| **결과물** | PDF 파일. `@capacitor/filesystem` + `@capacitor/share` 추가 필요 |

**빌드 도구가 없다는 점이 여기서 가장 크게 작용한다.** jsPDF UMD 번들(수백 KB)을
`assets/`에 직접 넣고 버전을 손으로 관리하게 된다. `.assetsignore`·배포 용량·라이선스
표기가 전부 따라온다.

**한 가지 이점**: 결과물이 **파일**이라 인쇄 대화상자를 거치지 않는다. 유저가 "PDF 저장"을
원할 때 클릭이 줄어든다. 다만 후보 A의 시스템 대화상자에도 PDF 저장이 있다.

**권하지 않는다.** 얻는 것(파일 직접 생성)에 비해 버리는 것(조판 161줄)이 크다.

### 후보 C — 서버 렌더링 PDF (Cloudflare Browser Rendering)

| | |
| --- | --- |
| **비용** | **높음 + 운영비 발생** |
| **인쇄 CSS** | 재사용 가능하지만 **서버에서 접근 가능해야 한다** |
| **Pro 게이트** | **서버로 옮겨진다 — 이건 개선이다** |
| **웹 경로** | 웹·앱 동일해진다 |
| **결과물** | PDF 파일 |

**구조적 문제**: **[코드]** 조판이 전부 클라이언트에 있다(§1). 서버가 PDF를 만들려면
`buildDiaryBookPages()`가 만드는 DOM을 서버에서 재현하거나, 클라이언트가 만든 HTML을
서버로 올려야 한다. 전자는 코드 이중화, 후자는 **감정 기록에 준하는 내용을 서버로
올리는 것**이라 **[방침]** §3의 "AI 요청 원문을 별도 대화 이력으로 저장하지 않으며"와
인접한 영역에 들어간다. 저장하지 않고 렌더링만 해도 **처리방침 재검토가 필요하다.**

**유일하게 이것만 되는 것**: 세 플랫폼(웹·Android·iOS)이 **바이트 단위로 같은 PDF**를
낸다. 책이 제품의 얼굴이라면 값어치가 있다.

**운영비**: **[확인 필요]** Cloudflare Browser Rendering 과금. `docs/pricing-system-v2.md`의
AI 예산 1,200원/월 · 미할당 예비비 100원 구조에 **새 비용 라인이 하나 생긴다.** 북은
이미 가장 비싼 단일 동작이고(**[코드]** `plan-policy.mjs:112` — `diary_book: 10`),
여기에 렌더링 비용이 더해진다.

**한 가지 짚을 것**: `pricing-system-v2.md`에 이미 적힌 원칙 — "에너지로 과금되는 항목은
별도 비용 라인에 다시 계상하지 않는다"는 **AI 비용**에 대한 것이다. 렌더링은 AI가 아니라
인프라 비용이라 그 원칙이 덮지 않는다. 예비비 100원에서 나가야 한다.

### 후보 E — 조용한 실패만 없앤다 (바닥) — **절반 적용됨**

기능을 되살리지 않고 **60초 창만** 없앤다.

**적용한 것 (실기기 관측이 필요 없는 부분)**

**[코드]** `printDiaryBook()`이 되돌리기를 세 신호에 건다:

| 신호 | 언제 |
| --- | --- |
| `afterprint` | 정상 경로 |
| `visibilitychange` → visible, `pointerdown`, `keydown` | **유저가 앱으로 돌아왔다.** 인쇄 대화상자가 앞에 있었다면 이미 닫혔고, 열린 적이 없다면 즉시 되돌리는 것이 맞다 |
| 60초 | 마지막 보루. 그대로 뒀다 |

입력 리스너는 **`window.print()`가 돌아온 뒤에** 단다. 데스크톱 브라우저는 `print()`가
대화상자가 닫힐 때까지 블로킹하므로 그 시점이면 이미 `afterprint`가 지나갔고, 그때는
리스너를 달지 않는다. 호출 **전에** 달면 대화상자를 여는 그 클릭이 곧바로 되돌려 버린다.

연속 클릭도 막았다. 이전 호출의 `restore`를 먼저 부르지 않으면 `previousTitle`이
"올리 다이어리 북 …"으로 굳는다.

**타임아웃을 줄이는 것으로 대신하지 않은 이유**: 인쇄가 비동기인 브라우저에서 조판이
끝나기 전에 되돌리면 출력이 깨진다. "유저가 앱을 보고 있다"는 신호에는 그 위험이 없다.

**미룬 것 (실기기 관측이 필요한 부분)**

**[확인 필요]** `beforeprint`가 오는지, `matchMedia("print").matches`가 참이 되는지.
그 둘이 반응해야 "인쇄가 시작되지 않았다"를 **판정**하고 정직한 메시지를 띄울 수 있다.
반응하지 않으면 판정이 짧은 타임아웃 추정으로 떨어지고, 느린 기기에서 정상 인쇄를
오탐한다. **그래서 판정과 메시지는 넣지 않았다** — 지금 넣으면 웹에서 되던 인쇄가
깨질 수 있다.

**이건 다른 후보의 대안이 아니라 바닥이다.** A를 하든 C를 하든, 어떤 경로로도 인쇄가
시작되지 않았을 때의 처리는 있어야 한다.

## 5. 권고

**E를 먼저 하고, A를 검증한다.**

1. **E는 무조건이다.** 어느 후보를 고르든 "인쇄가 시작되지 않았다"의 처리가 필요하고,
   지금 그 자리에 60초 함정이 있다. 비용이 몇 줄이다.
2. **A가 유력하다.** 인쇄 CSS 161줄을 그대로 쓰는 유일한 저비용 경로다. 다만
   **[확인 필요]**가 둘 남았다 — 플러그인의 Capacitor 8 지원, 그리고 Android가
   `@media print`를 적용해 인쇄하는지.
3. **C는 "책이 제품의 얼굴인가"에 달렸다.** 세 플랫폼 동일 출력과 서버 게이트가
   값어치 있다면 정당하다. 다만 **비용 라인이 하나 늘고 처리방침을 다시 봐야 한다.**
   지금 결정할 문제가 아니다.
4. **B는 권하지 않는다.** 조판 161줄을 버리고 번들러 없이 UMD를 손으로 관리하는 대가가
   얻는 것보다 크다.
5. **D는 A가 확인될 때까지의 임시 조치로만.**

**순서를 이렇게 두는 이유**: A·C는 실기기 관측 없이는 고를 수 없다(§0의 [미검증]).
E는 관측과 무관하게 지금 옳다.

## 6. 실기기에서 먼저 확인할 것

`docs/capacitor-shell-checklist.md`의 A-9/B-9에 붙는다. **Pro 계정 필요.**

1. `window.print()` 호출 시 콘솔에 예외가 찍히는가 (`Unable to open print dialog`)
2. `body.is-printing-book`이 붙은 채로 60초 유지되는가
3. `beforeprint` / `matchMedia("print")`가 반응하는가 — **후보 E의 남은 절반이 여기 달렸다**
4. **화면을 한 번 탭하면 `document.title`이 즉시 원래대로 돌아오는가** — 위에 적용한
   탈출 경로가 실제로 도는지. 안 돌면 60초를 기다려야 한다
5. **`.md` 내보내기(`exportRecordsFile()`)가 실제로 파일을 저장하는가** — §0.1.
   **인쇄보다 먼저 확인할 것**

절차는 `docs/capacitor-shell-checklist.md`의 **A-9(`.md`) → A-10(인쇄)** 순서에 넣었다.
`.md`가 앞인 이유는 §0.1대로 깨졌을 때의 무게가 다르기 때문이다.

**[미검증]** 이 문서의 후보 A·C 판단과 E의 남은 절반은 전부 위 다섯의 결과에 달려 있다.
특히 3번이 안 되면 E의 판정이 타임아웃 추정으로 떨어지고, 그건 정상 인쇄를 오탐한다.
