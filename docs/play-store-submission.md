# 1. 데이터 안전(Data safety) 양식 초안

## 1.0 판정 규칙 두 가지

**"수집(collected)"** — 앱이 기기 밖으로 내보내는 데이터. 기기 안에만 있으면 수집이 아니다.
이 규칙 때문에 **대화 로그는 수집 항목이 아니다** — `omwChatLog`는 계정 스코프
`localStorage`에만 있고 서버 동기화 목록에 없다(**[코드]** `script.js:328-335`의
`SERVER_SYNC_STORAGE_KEYS`에 `CHAT_LOG_KEY`가 없음, 테스트로 고정 →
`chat-log-storage.test.mjs`).

**"공유(shared)"** — 제3자로 **이전**. 다만 우리를 대신해 처리하는 **수탁자(service
provider)** 로의 이전은 구글 정의상 공유가 아니다. Cloudflare·OpenAI·토스페이먼츠·소셜
로그인 제공자는 전부 수탁 관계이므로 **공유 없음**으로 신고하는 것이 현재 판단이다.
근거는 §1.3에 따로 적었다 — 이 판단이 뒤집히면 양식 전체가 바뀐다.

## 1.2 표로 담기지 않는 예외 셋

**① 출생지는 수집하지만 쓰지 않는다.** **[코드]** `script.js:1449`에서 저장하고
`script.js:1435`에서 폼에 되돌려 넣는 것 외에 **읽는 곳이 없다.** 만세력 계산은
생년월일·시각만 받는다(`script.js:3707`). 게다가 `omwPersonalityProfile`은 서버 동기화
대상이라(`script.js:329`) 이 값이 서버까지 간다.

목적 없는 개인정보 수집이고, 데이터 안전 양식은 **항목마다 목적을 요구한다.** 적을 목적이
없다. 최소수집 원칙에서도 불리하다. **입력 필드를 지우는 쪽을 권한다** — 제품 코드 수정이라
이번 회차에서는 하지 않았다.

**② 이메일은 결제 이력이 있으면 탈퇴 후에도 5년 남는다.** **[코드]**
`auth-service.mjs:1076-1092`가 법정 보관 레코드에 `email`을 **평문으로** 넣는다
(`auth-service.mjs:1081`), 보존 기간은 `LEGAL_PAYMENT_RETENTION_MS = 5년`
(`auth-service.mjs:16`). 회원 참조값은 HMAC으로 가명화하는데(`auth-service.mjs:1080`)
이메일만 평문이다. **[방침]** §4 표에 "이메일, 가명화 회원 참조값"으로 이미 공시돼 있으므로
방침과 코드는 일치한다. 다만 데이터 안전 양식의 **"삭제 요청 가능"** 칸에는 이 예외를
반영해야 한다 — 구글은 "일부 데이터는 법령상 보관"을 허용한다.

**③ 체험 남용 마커는 탈퇴 후 1년 남는다.** **[코드]**
`ai-credits-service.mjs:544-556`, 보존 `TRIAL_ABUSE_RETENTION_MS = 365일`
(`ai-credits-service.mjs:50`). 키는 `ai-trial-used:<userId>`인데 그 `userId`가 이미
HMAC 값이라(`auth-service.mjs:275-278`) **[방침]** §4의 "일방향 계정 식별값" 서술과
코드가 일치한다. 저장 내용은 `usedAt`·`expiresAt`·`policyVersion`·`purpose`뿐이고
이름·이메일은 없다.

## 1.3 공유(제3자 전송) 판정

| 수신자 | 무엇이 가는가 | 판정 |
| --- | --- | --- |
| OpenAI | 목표·현재 계획·상태·메시지 등 요청 내용 | **수탁**. **[코드]** 네 호출 지점 모두 `store: false`로 OpenAI 측 저장을 끈다 — `ai-companion-chat.mjs:203`, `ai-diary-book.mjs:144`, `ai-goal-plan.mjs:261`, `ai-plan-revision.mjs:374`. **[방침]** §3의 "저장 비활성화 설정을 사용합니다"와 일치 |
| Cloudflare | 호스팅·저장 전반 | 수탁 |
| 토스페이먼츠 | 고객·주문·결제 식별자 | 수탁 (결제 활성화 시) |
| Google·Kakao·Naver | 로그인 식별 정보 | 수탁 |

**따라서 "데이터를 제3자와 공유합니까?" = 아니오**로 신고하는 것이 현재 판단이다.

**[확인 필요]** 이 판단은 각 사와의 계약이 실제로 처리위탁 관계인지에 달렸다. OpenAI는
API 이용약관상 입력을 모델 학습에 쓰지 않는다고 밝히고 있으나 **계약 문면을 직접 확인한
기록이 이 리포에 없다.** 제출 전에 확인해야 한다.

## 1.4 삭제 요청 경로 (양식의 "데이터 삭제 요청" 칸)

**[코드]** `auth-service.mjs:1029-1121`.

1. 앱 내 `/delete-account` → 로그인 세션 + "계정 삭제" 확인 문구(`auth-service.mjs:1036`)
2. 즉시 삭제: 소셜 연결(`deleteIdentitiesByUserId`), 세션(`deleteSessionsByUserId`),
   서버 동기화 데이터(`deleteAppState`) — `auth-service.mjs:1104-1106`
3. 회원 레코드는 7일 만료의 삭제 예정 레코드만 남는다
   (`ACCOUNT_DELETION_GRACE_MS`, `auth-service.mjs:15`)
4. 웹 경로도 함께 제공: privacy@olivenrich.com

구글은 **앱 내 경로와 웹 경로를 둘 다** 요구한다. 둘 다 있다.

**[확인 필요]** 구글은 "계정 삭제 요청 URL"이 **로그인 없이 접근 가능**할 것을 요구한다.
`/delete-account` 페이지가 비로그인 상태에서 무엇을 보여주는지 확인해야 한다.

## 1.5 스토어 IAP와 푸시가 들어오면 바뀌는 칸

| 칸 | 지금 | 바뀐 뒤 | 왜 |
| --- | --- | --- | --- |
| Financial info → Purchase history | 예(토스, 비활성) | 예(Google Play) | 구매 토큰·상품 ID·구독 상태를 우리가 보관한다 — `docs/entitlement-schema-draft.md` |
| Device or other IDs | **아니오** | **예** | 푸시 토큰은 기기 식별자다. **목적은 "앱 기능" 하나다** — v1은 이용자가 설정한 일정에 대한 서비스 알림만 보낸다(§2.1). "광고 또는 마케팅"은 붙이지 않는다 |
| Personal info → User IDs 목적 | 계정 관리, 사기 방지 | + 결제 이력 대조 | 스토어 구매를 계정에 붙이려면 매핑이 필요하다 |
| 삭제 요청 경로 | 위 그대로 | + 푸시 토큰 폐기 | 탈퇴 시 토큰도 지워야 한다 |

**푸시 목적은 확정됐다 — 서비스 알림뿐이다.** 무엇이 서비스 알림이고 무엇이 광고성인지,
그리고 나중에 광고성으로 넘어가려면 무엇이 선행돼야 하는지는 **§2.1**에 적었다.
이 결정 때문에 위 표의 "목적" 칸이 하나로 좁아지고, **[방침]** §2의 "마케팅 동의를
수집하지 않으며"는 지우지 않고 그대로 둔다.

## 2.1 푸시 경계 — v1이 무엇을 보내고 무엇을 보내지 않는가

**v1은 이용자가 스스로 설정한 일정에 대한 서비스 알림만 보낸다. 마케팅·리텐션 푸시는
보내지 않는다.** 그래서 §2의 "마케팅 동의를 수집하지 않으며"는 **그대로 둔다** — 지울
문장이 아니라 지켜야 할 약속이다.

이 경계는 코드로도 이미 그렇다. **[코드]** 지금 앱의 유일한 알림은 집중 타이머가 끝났을
때의 로컬 `Notification`이고(`script.js:7971`), 그것도 유저가 타이머를 **직접 시작한**
뒤에만 권한을 묻는다(`script.js:7998`). 푸시 토큰도, 서버 발송 경로도 없다.

### 무엇이 서비스 알림이고 무엇이 광고성인가

**기준은 하나다: 이용자가 스스로 만든 약속을 되짚어 주는가, 아니면 우리가 이용자를
다시 데려오려고 보내는가.** 발송 시각이나 문구의 부드러움이 아니다.

| 보낸다 — 서비스 알림 | 보내지 않는다 — 광고성 |
| --- | --- |
| "오늘 아침 7시 운동, 곧 시작이에요" (유저가 그 시각에 그 일정을 넣었다) | "3일째 안 오셨어요. 올리가 기다려요" (**리텐션**. 유저가 요청한 적 없다) |
| "집중 시간 25분이 끝났어요" (유저가 타이머를 눌렀다) | "이번 주 Pro 20% 할인" (**판촉**) |
| "체험이 오늘 밤 끝나요" (유저가 시작한 체험의 상태 변화) | "새 기능이 나왔어요, 보러 오세요" (**기능 홍보**) |
| "결제가 실패해 3일 뒤 잠겨요" (계약 이행에 필요한 고지) | "친구를 초대하면 크레딧을 드려요" (**추천 유도**) |
| "다른 기기에서 로그인됐어요" (보안 고지) | "작년 오늘 이런 목표를 세우셨네요" (**회고 미끼**. 되짚음처럼 보이지만 유저가 요청한 알림이 아니다) |

마지막 줄이 실제로 헷갈리는 자리다. **판단 순서**: ① 유저가 이 알림을 **명시적으로
설정했는가** → 아니오면 광고성. ② 계약 이행·보안·법정 고지인가 → 아니오면 광고성.
**애매하면 광고성으로 분류한다.** 잘못 분류했을 때 한쪽은 알림이 하나 줄고, 다른 쪽은
정보통신망법 위반이다.

### 광고성 푸시를 보내려면 무엇이 선행되어야 하는가
